# Application One

Sample Spring Boot microservice used to demonstrate the [`release-automation`](https://github.com/saghosh8/release-automation) platform end-to-end — repository scaffolding, CI, tagged releases, and environment deployments.

This repository was generated by `release-automation`'s **Create Application Repository** workflow from `input_files/app_config.yaml`, and its `APP_NAME` (`application-one`), Java package (`com.example.applicationone`), and main class (`ApplicationOneApplication`) were all derived automatically from the repository name at creation time.

## About

Application One is a minimal Spring Boot 3 web service. It exists to be a realistic, deployable target for the release-automation pipeline — it has a real build, a real container image, a real Helm chart, and real Dev/UAT/Prod deploy workflows, but intentionally simple application logic (one REST endpoint and Spring Actuator health checks).

## API Endpoints

| Method | Path                          | Description                                             |
| ------ | ------------------------------ | -------------------------------------------------------- |
| GET    | `/api/v1/hello`                 | Returns `{"application": "application-one", "status": "running"}` |
| GET    | `/actuator/health`               | Overall Spring Boot Actuator health status               |
| GET    | `/actuator/health/readiness`     | Kubernetes readiness probe endpoint (used by the Helm deployment) |
| GET    | `/actuator/health/liveness`      | Kubernetes liveness probe endpoint (used by the Helm deployment) |
| GET    | `/actuator/info`                 | Actuator info endpoint                                   |

Only `health` and `info` actuator endpoints are exposed (`management.endpoints.web.exposure.include: health,info` in `src/main/resources/application.yml`), and health probe groups are enabled (`management.endpoint.health.probes.enabled: true`), which is what makes `/actuator/health/readiness` and `/actuator/health/liveness` available for the Helm deployment's probes.

The app listens on port `8080` (`server.port` in `application.yml`, and `EXPOSE 8080` in the Dockerfile).

## Build, Test, and Run

Requires JDK 17 and Maven.

```bash
# Run the unit tests (currently just a Spring context load test)
mvn -B test

# Build the jar
mvn clean package

# Run locally
mvn spring-boot:run
```

Once running locally:

```bash
curl http://localhost:8080/api/v1/hello
curl http://localhost:8080/actuator/health
```

## Docker

The `Dockerfile` is a two-stage build:

1. **Build stage** (`maven:3.9-eclipse-temurin-17`) — resolves dependencies offline, then compiles and packages the jar with `mvn -B clean package -DskipTests`.
2. **Runtime stage** (`eclipse-temurin:17-jre-alpine`) — copies only the built jar into a minimal JRE image, runs as a non-root `appuser` (uid/gid 1000), exposes port `8080`, and defines a container-level `HEALTHCHECK` that polls `/actuator/health`.

```bash
docker build -t application-one:local .
docker run -p 8080:8080 application-one:local
```

## Configuration

`src/main/resources/application.yml` is the only file Spring Boot itself reads. It sets the application name, server port, and which actuator endpoints/probes are exposed.

The three files under `config/` are **not** loaded by the Spring Boot application — they're metadata consumed by the release-automation tooling and by whatever process reads them for release decisions, not by the running service:

| File                        | Purpose (as data)                                                                 |
| ---------------------------- | ----------------------------------------------------------------------------------- |
| `config/application-config.yaml` | Declares the app's name/version, its current deployment environment and replica count, and feature toggles (`databaseChange`, `notification`, `fraudCheck`). |
| `config/release-config.json`     | Declares release metadata (version, environment, whether this release includes a database change) and deployment rules (whether to create a release branch / pull request). |
| `config/services.json`           | A small registry of related services (`application-one`, `notification-service`, `fraud-service`) and whether each is currently enabled. |

If you're wiring these into an actual decision process (e.g. gating deploys on `databaseChange`), that logic lives outside this repository — today they're static, hand-maintained descriptors.

## Helm Chart

Chart: `helm/application-one/` (`Chart.yaml`, appVersion `1.0.0`).

Per-environment values files override the shared defaults in `values.yaml`:

| Setting                | `values.yaml` (default) | `values-dev.yaml` | `values-uat.yaml` | `values-prod.yaml` |
| ------------------------ | ------------------------ | ------------------- | ------------------- | --------------------- |
| `replicaCount`            | 1                          | 1                    | 2                    | 3                      |
| `environment.SPRING_PROFILES_ACTIVE` | `dev`         | `dev`                | `uat`                | `prod`                 |
| `features.notification`   | `false`                    | `false`              | `true`               | `true`                 |
| `features.fraudCheck`     | `false`                    | `false`              | `false`              | `true`                 |
| `features.databaseChange` | `false`                    | `false`              | `false`              | `true`                 |
| `autoscaling.enabled`     | `false`                    | (inherited: `false`) | (inherited: `false`) | `true` (3–8 replicas, 70% CPU target) |

The chart renders:

- **Deployment** — one container (`application-one`) on port 8080, environment variables from `.Values.environment`, readiness probe at `/actuator/health/readiness`, liveness probe at `/actuator/health/liveness`, and resource requests/limits from `.Values.resources`.
- **Service** — `ClusterIP` by default, forwarding `service.port` → `service.targetPort` (both 8080 by default).
- **Ingress** — only rendered if `ingress.enabled` is `true` (disabled by default; not set to `true` in any of the environment values files as checked into this repo).
- **HorizontalPodAutoscaler** — only rendered if `autoscaling.enabled` is `true` (enabled in `values-prod.yaml` only).
- **ConfigMap** — exposes `APP_VERSION`, `SPRING_PROFILES_ACTIVE`, and the three feature-flag values as config data (note: the Deployment does not currently mount or reference this ConfigMap — the same values are instead injected directly as environment variables from `.Values.environment`).

## CI/CD Pipelines

This repository's own Actions workflows are triggered directly (manual `workflow_dispatch` in this repo) **and** remotely by `release-automation`'s `prod_ci.yml` / `prod_cd.yml`, which look these workflows up by name (`CI`, `CD - Prod`) and dispatch them on a target branch.

### `CI` (`.github/workflows/ci.yml`)

Trigger: `workflow_dispatch`

1. **Build & Test** — sets up JDK 17, runs `mvn -B test`, then `mvn -B clean package -DskipTests`.
2. **Validate Helm Chart** — lints the chart (`helm lint`) and renders it with `values-dev.yaml` as a sanity check.
3. **Build & Push Image** — runs only if both jobs above pass, and only on `main`, `release/*`, or `feature/*` branches. Logs into `ghcr.io`, builds the Docker image, and pushes it tagged `latest`, the full commit SHA, and the short (7-char) commit SHA. The short SHA is echoed to the job summary as the `image_tag` to use for `CD - Dev` / `CD - UAT`.

### `CD - Dev` (`.github/workflows/cd_dev.yml`)

Trigger: `workflow_dispatch` with input `image_tag` (default `latest`).

Spins up a local `kind` cluster (`demo-dev`), creates a `dev` namespace, and `helm upgrade --install`s the chart with `values-dev.yaml`, overriding `image.tag` with the given input. Prints the resulting pods/deployment/service/HPA and the replica count.

### `CD - UAT` (`.github/workflows/cd_uat.yml`)

Same shape as `CD - Dev`, but targets a `demo-uat` kind cluster, the `uat` namespace, and `values-uat.yaml`.

### `CD - Prod` (`.github/workflows/cd_prod.yml`)

Trigger: `workflow_dispatch` with required input `release_tag` (e.g. `1.0.0-release-81269a6` — the format produced by `release-automation`'s publish workflow).

1. Parses `release_tag` into its short commit SHA and version (splitting on the last `-release-`).
2. Spins up a `demo-prod` kind cluster and a `prod` namespace.
3. Deploys with `values-prod.yaml`, forcing `autoscaling.enabled=false` for the deploy step itself (the chart's own prod HPA settings are not used here) and setting `image.tag` to the **short commit SHA** parsed from the release tag — not the full release tag string.
4. On failure, dumps pod status, `kubectl describe pods`, and recent events for diagnosis.
5. On success, prints the deployed release tag, pods, deployment/service/HPA, and replica count.

This is the workflow `release-automation`'s `prod_cd.yml` triggers, passing `release_tag` as read from `input_files/prod_New_tag.txt` in that repository.

## Relationship to release-automation

- **Created by:** `release-automation`'s Create Application Repository workflow, from `input_files/app_config.yaml` in that repo.
- **Release-branched by:** `release-automation`'s Create Release Branches workflow (`release/<name>_<version>`).
- **Tagged and released by:** `release-automation`'s Create and Publish Release Notes workflow, which creates tags of the form `<version>-release-<short-sha>` and publishes the GitHub Release for this repository.
- **CI triggered by:** `release-automation`'s Trigger CI Pipeline workflow (`prod_ci.yml`), which dispatches this repo's `CI` workflow on the release branch.
- **Prod deploy triggered by:** `release-automation`'s Trigger CD - Prod Pipeline workflow (`prod_cd.yml`), which dispatches this repo's `CD - Prod` workflow with the release tag as `release_tag`.

See the [release-automation README](https://github.com/saghosh8/release-automation#readme) for the full cross-repository release flow.

## Troubleshooting

**`helm lint` or `helm template` fails in CI** — run the same commands locally from the repo root: `helm lint helm/application-one` and `helm template application-one helm/application-one -f helm/application-one/values-dev.yaml`.

**Image push fails in CI** — confirm the workflow has `packages: write` permission (already set for the `publish` job) and that the built image tag doesn't collide with an immutable existing tag in GHCR.

**`CD - Prod` deploys the wrong image** — check that `release_tag` is well-formed (`<version>-release-<short-sha>`); the workflow derives the deployed `image.tag` purely from the substring after the last `-release-`, so a malformed tag will resolve to the wrong (or an empty) image tag.

**Probes failing after deploy** — confirm `/actuator/health/readiness` and `/actuator/health/liveness` return 200 inside the cluster; both require `management.endpoint.health.probes.enabled: true`, which is already set in `application.yml`, but a profile override could disable it.
